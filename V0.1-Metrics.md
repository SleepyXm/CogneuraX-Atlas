# V0.1 retrieval metrics

## Status

This is the recorded baseline for the retrieval architecture carried into CogneuraX Atlas. It was measured on 7 real project documents with a frozen prompt map of 14 previously unseen questions. The prompts, expected sources, and thresholds were fixed before the results were inspected.

The result measures evidence retrieval only. It does not measure generated-answer quality because Atlas does not call the user's answer model.

## Results

| Metric | Result | Definition |
| --- | ---: | --- |
| Answer-bearing evidence | 9/12 (75.0%) | An answerable question returned at least one chunk from the expected document containing an accepted answer string. |
| Expected source returned | 9/12 (75.0%) | The expected document appeared anywhere in the returned evidence for an answerable question. |
| Expected source ranked first | 7/12 (58.3%) | The first returned chunk came from the expected document. |
| Unanswerable rejection | 1/2 (50.0%) | An unanswerable question correctly returned no chunks. |
| Mean retrieval latency | 15 ms | Mean API retrieval time across the frozen prompt map. |
| Maximum retrieval latency | 45 ms | Slowest API retrieval time across the frozen prompt map. |

The 75% figure refers specifically to answer-bearing evidence for the 12 answerable prompts. It is not a combined score and should not be described as general RAG accuracy.

## Evaluation set

The corpus contained these seven documents:

1. Project README
2. Project architecture and implementation contract
3. Experimental ingestion notes
4. Shared UI documentation
5. Backend dependency manifest
6. Knowledge processor dependency manifest
7. Project licence

The prompt map contained:

- 12 answerable questions whose expected document and accepted answer strings were declared in advance.
- 2 deliberately unanswerable questions that were required to return no evidence.

The questions covered project configuration, architecture constraints, rejected model experiments, UI conventions, dependency versions, and licence terms. The prompt map was frozen after definition; it must not be edited to improve the recorded score.

## Retrieval configuration

| Setting | V0.1 value |
| --- | --- |
| Dense model | `BAAI/bge-small-en-v1.5` |
| Sparse model | `Qdrant/bm25` through FastEmbed |
| Dense threshold | `0.55` |
| Sparse threshold | `5.0` |
| Lowest relevant dense calibration score | `0.9033` |
| Highest irrelevant dense calibration score | `0.5460` |
| Lowest relevant sparse calibration score | `5.1034` |
| Highest irrelevant sparse calibration score | `3.3931` |

The retrieval path was:

1. Embed the question for dense routing.
2. Select documents whose typed dense routes pass the dense threshold.
3. Search complete chunks from those documents with BM25.
4. If scoped BM25 returns no accepted chunks, run the permitted whole-collection BM25 fallback.
5. Return the accepted evidence without answer generation or reranking.

## What failed

The primary failure was the handoff between semantic document routing and lexical chunk retrieval. Dense routing could select the correct document, but BM25 could still reject its answer-bearing chunk when the question and source used different wording.

The whole-collection fallback then created a second failure mode: an unrelated chunk with stronger token overlap could pass the sparse threshold and be returned as evidence. This explains both the missed answerable questions and one of the two false-positive unanswerable results.

No single sparse-threshold change solved both problems: lowering it admitted more irrelevant chunks, while raising it discarded more relevant chunks.

## Interpretation

V0.1 proves that the staged dense-document/sparse-chunk pipeline works end to end and retrieves useful evidence with low query latency. It does not yet establish production retrieval quality. In particular:

- One quarter of answerable questions did not return answer-bearing evidence.
- More than two fifths of answerable questions did not rank the expected source first.
- Half of the unanswerable questions returned a false positive.

Hardware affects ingestion throughput, especially the local Qwen routing pass, but it does not explain these retrieval errors. They are ranking and matching errors.

## Reproducibility boundary

These figures were produced by the original frozen evaluation before the standalone Atlas extraction. The current Atlas repository contains the calibration fixture in `testdata/retrieval.json`, but it does not yet contain the complete seven-document corpus or an automated runner for the 14-prompt evaluation. Until those are added and the benchmark is rerun unchanged, these numbers remain the recorded V0.1 baseline rather than a newly reproduced Atlas result.

Future changes must be calibrated on a separate development set and judged on a fresh unseen holdout. Reranking, dense chunk vectors, score fusion, or a query-time model pass are architecture experiments and must be recorded explicitly instead of being introduced as hidden threshold tuning.
